# Install the guided kit

Briefly explain the local work and what the member will see, then do it within the existing authorization. Keep the selected business project, account and actual entitled tier. An available tool, a folder name or a local license file alone is not proof of a subscription. Do not search other accounts or private application caches.

1. Inspect the supplied filenames/index once. Identify the complete selected-tier ZIP and any business-data files. Reuse an approved ZIP already present. A few copied documents are not a kit.
2. If the connected service actually exposes `get_kit_download`, read its real schema and use the authenticated selected-tier response. Save the small descriptor and run the verified `download_kit.py` on the device. It streams one complete ZIP, checks size/hash and rejects redirects or a different origin. This new route is a publisher integration requirement: do not assume it is live because a plugin version changed. If unavailable, use the complete ZIP provided by support/onboarding. Give that single missing-file step only when necessary. Never call GetKitFile hundreds of times or relay bulk/base64 through the conversation. A real 403 or entitlement refusal stops that service path.
3. Use [local helper delivery](references/local-helpers.md). The complete tier ZIP now includes the pinned `Install tools/` files, so it can also serve as the helper carrier. Core's small bootstrap can extract exactly those helpers on the selected device. Do not reconstruct them or confuse a cloud path with a device path.
4. Run the exact archive planner with the selected tier, release and independently supplied archive hash. Run `install_kit.py` with the same arguments and `--mode fresh` for absent/exact package targets, or `--mode companion` for an existing same-tier workspace. The installer verifies every packed file. It never replaces client root files, executes an engine or creates a schedule. A companion is a complete separate guide inside this business folder; its verified receipt names the actual guide path.
5. Read back the installation receipt and `.caiman/active-guidance.json`, then run the selected guide's read-only status against the **business project root**. The receipt explicitly distinguishes packed archive counts from server-expanded file counts. Neither count is compared with the other. Installation is not setup completion.
6. Continue the requested setup/review: existing sources and scoped memory, initial historical inventory, deterministic source preparation, actual dashboard and one next step. The client does not run commands or choose skills.

The full commands and migration boundary are in [install intake](references/install-intake.md). Root instructions, memory, history, prior outputs and existing engines remain intact. Use the VIP guide's specific inspect/apply/backup/rollback updater for a recognized initialized runtime; do not use the generic installer to replace engines. Unknown/edited runtimes and Alan's older Windows repair chain retain their support path. GLS uses its own guide and manual seller evidence; it does not gain VIP/SP-API/schedule authority.

A complete local archive receipt proves matching bytes at the selected local path. It does not prove live subscription entitlement, server freshness, account connection, completed onboarding or an operating week. Ordinary returning work reuses the saved active guide and selected resource; do not re-download or hash the entire kit every turn.

Installation retains its staging files and uses a persistent OS lock that releases when the helper exits. It does not need permanent-delete permission. Do not request broad deletion just to tidy temporary files; cleanup is optional and separate. A failed attempt preserves partial new files for exact-byte resumption.
