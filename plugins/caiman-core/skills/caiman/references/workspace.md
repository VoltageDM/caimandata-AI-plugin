# Several brands: the workspace

Many members run more than one brand, more than one Amazon account, or both. Each brand keeps its own business folder (its kit, its files, its Amazon account), and nothing moves. The **workspace** is the folder that holds those business folders. The member opens it, and one message, or one scheduled task, works through every brand (or the ones they name), one brand at a time, and ends with one combined summary.

`scripts/workspace.py` in this skill's folder does the bookkeeping. It reads each brand's own files, never the connector, and never changes an Amazon account. Every command prints JSON with `member_message` in plain words. On Windows, use `py -3` where it says `python3` (the caiman skill, "Which Python command").

```
python3 "<caiman skill folder>/scripts/workspace.py" find        --workspace "<folder>"
python3 "<caiman skill folder>/scripts/workspace.py" init        --workspace "<folder>"
python3 "<caiman skill folder>/scripts/workspace.py" status      --workspace "<folder>"
python3 "<caiman skill folder>/scripts/workspace.py" plan        --workspace "<folder>" [--session "<session>"]
python3 "<caiman skill folder>/scripts/workspace.py" run start   <workflow> --workspace "<folder>" [--brands "<brand>,<brand>"] [--goal "<request>"]
python3 "<caiman skill folder>/scripts/workspace.py" run next    --workspace "<folder>" --run "<run>" --session "<session>" [--take-over <brand> | --leave <brand>]
python3 "<caiman skill folder>/scripts/workspace.py" run done    <brand> --workspace "<folder>" --run "<run>" --session "<session>" --status done|skipped|failed|needs-answer --note "..." --summary "<file>"
python3 "<caiman skill folder>/scripts/workspace.py" run reports <brand> --workspace "<folder>" --run "<run>" --session "<session>" --add "<read>=<report id>" [--failed "<read>=<what it said>"]
python3 "<caiman skill folder>/scripts/workspace.py" run status  --workspace "<folder>"
python3 "<caiman skill folder>/scripts/workspace.py" run finish  --workspace "<folder>" --run "<run>" [--partial]
python3 "<caiman skill folder>/scripts/workspace.py" summary     --workspace "<folder>"
python3 "<caiman skill folder>/scripts/workspace.py" update-plan --workspace "<folder>" [--live-kit <release> ...]
python3 "<caiman skill folder>/scripts/workspace.py" update      --workspace "<folder>" --zip "<kit zip>" [--zip "<other membership's kit zip>"]
python3 "<caiman skill folder>/scripts/workspace.py" routine     list|prompt [<workflow>] --workspace "<folder>"
python3 "<caiman skill folder>/scripts/workspace.py" dashboard   --workspace "<folder>" [--brands "<brand>,<brand>"]
```

A brand can be named by its ID (from `find`), its name, its folder or its connector brand slug.

## Recognize a workspace

- The folder you work in is a workspace when it has `CAIMAN WORKSPACE.json`, or when it has no kit of its own (no `RELEASE_MANIFEST.json` or `ENTITLEMENTS.json`) and holds two or more business folders, up to three levels down. Business folders deeper than that aren't part of it: when `find` (or the setup check) says they are further down, the workspace is the folder that holds them (for example `handoffs/2026-09-12-v1/brands`, or the folder above it): ask the member to open it, or use it as `--workspace`. Never install a kit in the folder you were given just because no business folder was found there. `find` looks at no more than 3,000 folders: opened on a home, Documents or Dropbox folder it stops there (`status: "too-many-folders"`, and the other commands refuse the same way) and says to open the folder that holds the brands' business folders instead. Ask the member which folder that is; don't search the home folder yourself. `find` says for sure (`is_workspace`) and lists each brand: its name, folder, connector brand slug, marketplace, saved seller ID and Ads profile ID, membership, kit version and VIP Machine. It skips `_previous-kit`, `_archive…`, `_retired` and backup folders.
- The workspace folder itself has no kit and needs none: never install a kit there, and don't treat it as a new business. Each brand's kit is in its own folder.
- The first time, run `init` (one sentence to the member first). It writes `CAIMAN WORKSPACE.json` (the brands, with their folders and accounts), a workspace section in the folder's `CLAUDE.md` between its own `CAIMAN WORKSPACE START` and `END` lines (the member's own text outside them stays exactly as it was; the file is created if it's missing) and `START HERE - all brands.md` with the messages to use. Run `init` again when a brand folder is added, moved or renamed: it picks up new brand folders and lists the ones it no longer finds.
- **The setup check** at a workspace checks every brand: run `setup_check.py` with the workspace folder as `--project-root` (one `list_brands` call covers them all). Each brand is checked in its own folder and keeps its own `CAIMAN STATUS.md`; the answer has one headline for all of them, with each brand's checks under `brands`. Open with that headline, and deal with each brand's items in that brand's folder.
- `find` flags what needs care. **Two folders bound to the same brand**: ask the member which folder is the current one; runs leave that brand out until then, and never merge or move folders without their OK. **Brands that share a seller account or Ads profile**: the usual way is one business folder for the account, each brand's products their own product families there (Caiman 0.3.38), and then there's nothing more to do here. When the member gave a brand a folder of its own (its own store, added with Add another store in the member's Caiman account): the account's reports include every brand's products, so each brand's work uses only its own products; read a report under the slug that asked for it (another slug's status answer is a 409 naming the right one), and run the brands' Search Query Performance one after the other, since they share Amazon's one line for the account; on VIP, each brand's VIP Machine needs its brand scope before its weekly review counts results: save the account's listings and variation families with that brand's slug (`search_listings`, every page, and `get_variation_family`), run `vip_machine.py brand-scope-check` with them, the member confirms which families are the brand's (`list_brand_asins` is only a cross-check), then `change-settings --brand-scope <file> --reason "<their words>"` (or `--whole-account`); the VIP Machine's README, "Brand scope". Until a choice is saved, its weekly review counts every product in the account, so `plan` puts saving it right after any kit updates ("Save <brand>'s brand scope", with the steps in its `how`), and a run flags that brand: in `run start`'s `alerts` and message, in its `task.rules` (`task.brand_scope_alert`) and under "I need from you" in the combined note's handoff, until the choice is saved. **Kits older than this plugin**: update them (below).

## Route the request

1. **All brands, or several named:** use the run flow below.
2. **One brand named:** work in that brand's business folder only, exactly as for a single business (sections 1 to 5 of the caiman skill, with that folder as the business folder). The workspace changes nothing about how one brand works.
3. **A request for one brand that names none** ("run the weekly review", "how are my ads doing?"): ask once, "Which brand, or all of them?" Requests that are clearly about all brands don't need the question.
4. **"What's next across my brands?"**, or "what's next?", "hi" or "I'm back" at the workspace: run `plan`. It runs each brand's `NEXT_STEP.py` (which never contacts Amazon; it refreshes that brand's own `CAIMAN PLAN.md` as usual) and merges the steps into one ranked plan, each labeled with its brand, in `WORKSPACE PLAN.md`. Right after any kit update come your own unfinished runs (kind `unfinished-run`: a run a session stopped partway; `still-to-do`: brands a run was finished without): carry each on without asking (its `agent_command`, `run next --run "<run>"`) and follow the run flow to its combined note. A run another session is still working through (a brand in it handed out less than 30 minutes ago, and none to the `--session` you pass) is left to it and said so (`in_progress_elsewhere`). Then give the next step as Next, in your own words with its brand, ending "Say next to start it."; the member's "next" (or a yes to it) starts it: do it in that brand's folder (its `agent_command`), then come back to the plan. When a VIP brand's business view was built before its brand scope was saved (so it covers the whole seller account), the plan puts a step to refresh that view first ("Refresh <brand>'s business view for just its own products": `REFRESH_OPERATING_VIEW.py`, which rebuilds it from the reports already saved), leaves out that brand's steps for product families outside its scope (listed under `left_out_by_brand_scope`), and marks its other steps `figures_cover`.
5. **"Show me all my brands":** run `summary`. It writes `WORKSPACE SUMMARY.html` (and `.md`) from each brand's latest saved outputs: the business view or VIP weekly dashboard, results due, what has worked, proposals waiting on the member and alerts. It changes nothing. Open the page and give the few points that need the member. Each figure says what it covers when that matters: with a VIP brand scope saved, a business view or VIP weekly dashboard built with it says "just this brand's products"; one built before it says "whole seller account", with a plain note (and, for the business view, what the brand's own product families sold in it, when they can be told apart). Say those figures cover the whole account, never present them as the brand's own, and refresh that brand's business view yourself (`REFRESH_OPERATING_VIEW.py` in its folder; it reads nothing new and changes nothing in the account), then run `summary` again and give its figures; its VIP weekly dashboard catches up at the next weekly review. A brand that shares its seller account with another brand here and has no scope saved gets the same "whole seller account" label.
6. **"Update all my brands":** the kit-sync skill, "Every brand in a workspace".
7. **"Show me the dashboard for all my brands"** (or how all the brands are doing): run `dashboard`. It builds each brand's Caiman Dashboard with that brand's own kit and merges them into one, with "All brands" and each brand; brands in different currencies are never added together. Publish and open it as the kit's `CAIMAN DASHBOARD.md` says ("Several brands").
8. **"Continue"** with a run still open: `run next`. When more than one run is unfinished it lists them instead: carry on with the one the member means (`--run`), never a scheduled task's run. With no run open, `run next` carries on the brands a current run was finished without (below).

`status` gives one table across the brands (kit, setup step, VIP Machine, last weekly review, results due, alerts) when you need to see where each one stands.

## The run flow

1. **Start.** Say in one sentence what will happen ("I'll run the Weekly Growth Review for your three brands, one at a time, and then give you one summary."). Run `run start <workflow>` with the brands the member named (`--brands`), or none for all; for a request that isn't one of the workflows, use `request` with their words in `--goal`. It saves `workspace-runs/<date> <workflow>.json` with each brand pending, and gives the first brand's `task`. Workflows: `deep-seed`, `weekly-growth-review`, `listing-creative-pack`, `stock-profit-plan`, `advertising-weekly-review`, `advertising-daily-check`, `advertising-structure-review`, `setup-check`, `request`, and on VIP the VIP Machine's routines: `vip-weekly-loop`, `vip-daily-brief`, `vip-health-check`, `vip-opportunity-review`. A brand a workflow doesn't apply to (a VIP Machine routine for a GLS+ brand, or a VIP brand whose machine isn't set up yet) is listed as skipped with the reason.
   **Reports first.** Amazon can take an hour or more to make some accounts' Ads reports, so for the Advertising Daily Check, the Advertising Weekly Review, the Weekly Growth Review and the VIP Machine's weekly loop, `run start` also lists every brand's reports to request before any brand's work (`prefetch`): each brand with its connector slug, its reads (each read's tool and its exact arguments, with that brand's own `brand_slug`) and a `record` command. Request each read with its arguments as given (never one brand's slug for another), and record the report IDs with that brand's `record` command (`run reports <brand> --add "<read>=<report id>"`; a Search Query Performance request answers at once with one `sqp_batch_id` for all its reports: record that); don't wait for the reports. Each brand's task then lists its reports in `task.reports`: poll the IDs in `requested` with the tool each read names in `poll_with` (`get_sqp_batch` for Search Query Performance, the whole call every 15 minutes or so, never its reports one by one; `get_ads_report_status` for Ads reports; that brand's slug) instead of requesting them again, and request the ones in `to_request` there. Run start lists at most four of a brand's reads, the slowest first, and its task asks for the rest as earlier ones finish, so no more than four of a brand's report requests are open at once, counting the ones its own work asks for (the daily check's keyword and target reads from `STOP_LINES.py due`). A request that errors is recorded with `--failed "<read>=<what it said>"`; a report that failed or expired when its brand's turn comes is requested again in that brand's own task and its new ID recorded the same way. Record only the `report_id`, never a download link. A brand with no connector slug saved, or one another session is working on, isn't in the list (`not_requested` says why). The reads: the daily check reads each ad type's campaigns with a row for each day (Sponsored Products, Brands and Display, one read each), yesterday and the 7 days before it, for yesterday's delivery and spend against the 7 days before, on the account's dates as the brand's own `STOP_LINES.py due` counts them (today's date in UTC when it can't be run; the task then says so, and `due` runs without `--date` and works out the account's date itself). Its Sponsored Products read is the one that `due` asks for (its delivery check and daily pass, the 14 newest days, `stop_lines_read`) whenever that covers those days, so Amazon is asked for those days once: save each read once, at its `save_as` in `Reports/stop-lines/<date>/` with the call that started it, where `STOP_LINES.py check` finds a read by its dates, and poll that ID when `due` names the read again rather than asking for it a second time (the brand's task says so, with the account's date to pass to `due`); a weekly review reads the last 30 days (search terms, placements, advertised products, campaigns), or, for a VIP brand whose VIP Machine is set up, the VIP Machine's four weeks and the last 7 complete days of search terms. For that brand's weekly loop or a Weekly Growth Review they also hold, first, the Search Query Performance weeks its weekly refresh needs (`WEEKLY_REFRESH.py plan --preview`, which saves nothing) and, last, the Sponsored Products reads of the newest four full weeks its growth moves take (the latest Saturday at least 8 days back and the 27 days before it; nothing is asked twice when those are the VIP Machine's weeks). A read its weekly refresh plans under the same name and arguments has its IDs recorded there too, with the refresh's `requested` command.
2. **Do one brand.** The `task` names the brand's folder, its account (`connector_brand_slug`, marketplace, seller ID, Ads profile ID) and how the workflow starts there for its membership: `CLIENT_START.py` from that brand's own kit, or, for a VIP Machine routine, that brand's own routine prompt with its folders. Do the workflow as the caiman skill says for one business, in that folder and with that account only, following `task.rules`. The brand's kit skills live in its own `.claude/skills/`, which the app doesn't load from the workspace folder: when `CLIENT_START.py` names a skill, read `<brand folder>/.claude/skills/<name>/SKILL.md` and follow it (the caiman skill, "How to work"). Record the brand's own work there as usual (`NEXT_STEP.py done` and `applied`, the VIP Machine's records); the run's record is extra, never instead.
3. **Close the brand.** Save a few lines in `task.summary_file` (that brand's own file; `run done` refuses another brand's): what was done, the numbers that matter, and what needs the member. For a weekly review, start with the brand's three lines (on VIP, `MONEY_LEAKS.py`'s: the biggest leak, the one move, the yes or no question; when a rule held the best move, the move line names the rule and what it held), then what its past changes did and its moves, at most 5. Save the brand's handoff in `task.handoff_file` (below, "The combined handoff"), there even when the summary you record is another file. Then record it with `task.when_done` (`run done <brand> --run "<run>" --status done --note "..." --summary "<file>"`), which reads the handoff too (from `task.handoff_file`, or beside a summary given from the brand's own folder) and says when it couldn't be used (`handoff_problems`) or when a done brand has none (`handoff_missing`, where to save it, and a warning, as for a missing summary): save it and record the brand again. A brand that failed is `--status failed`; one that needs the member's answer or approval is `needs-answer`; one that doesn't apply is `skipped`; say why in `--note`. `run done` warns when a summary or handoff names another brand's slug, seller ID or Ads profile ID: check it before going on.
4. **Next.** `task.next` (`run next --run "<run>" --session "<session>"`) gives the next brand. Always name the run: another chat or a scheduled task may have a run of its own open. Keep the `session` the first answer gave you: `task.next` and `task.when_done` already carry it, and it's how the run knows which brand is this chat's. Repeat until it says every brand has a result.
5. **Finish.** `run finish --run "<run>" --session "<session>"` (the `finish` command each answer gives) writes one combined note, `workspace-runs/<date> <workflow>.md`: a table of the brands' results, the brands still to do under "Still to do: I'll pick these up next", each brand's summary, and at the end one handoff, the shape every workflow ends with (below). Give the member the handoff in its own words. If a brand can't be done now, `run finish --partial` leaves it still to do.

**The combined handoff.** Each brand's handoff is a JSON file at `task.handoff_file` (`workspace-runs/<run>/<brand>.handoff.json`, beside the summary the task names): `{"done": "<one line: what was done>", "go": [{"change": "<one account change waiting for the member's go: the exact object, its value now and after, and the number behind it>", "ref": "<where it is in the brand's own records, such as its proposal ID>"}], "need": [{"ask": "<a fact only the member has>", "default": "<what is used meanwhile>"}], "next": "<what Caiman does next for this brand>"}`. Leave out a part with nothing in it; a `go` or `need` item may be a plain string. `run finish` puts every brand's together, in the run's brand order, as the note's last part (`handoff` in its answer; the run record and `run status --run "<run>"` keep it for a later session, without `next.command`, which holds this session's paths: `next.starts` says what starts it), leaving out an empty part:

- **Done**: one line for each brand (its `done`, else its note; "Didn't finish: ...", "Not done yet: I'll pick it up next.", or, for one a later run picked up, "Picked up in the run ...: its result is in that run's note."), with anything to check under it.
- **Your go**: every brand's `go` lines, numbered across the brands with the brand's name on each line, then "Reply go to make all of them, go 1 3 for some, or no 2 to skip one. Nothing changes until you reply." (with two changes, "go 1 for some"; with one, "Reply go to make it, or no to skip it. Nothing changes until you reply.")
- **I need from you**: each brand's facts with the default used meanwhile ("Meanwhile: ..."), a brand waiting on an answer with its note, and a brand scope still to save.
- **Next**: the brands the run didn't get to, else another unfinished run, else the brands' own `next` lines, else the plan across the brands, ending "Say next to start it." (`handoff.next.command` starts it, when it has one).

When the member replies, `go` only approves and `next` only starts. Make exactly the numbered changes they approved, each in its own brand's folder with its own account (the brand on its line, `handoff.go`, with its `ref`), check that each landed and record it there as that brand's kit says; `no 2` skips that one. A scheduled run's handoff waits for the member's reply in a conversation: the run changed nothing.

**A stopped run picks up at the next brand.** Nothing is lost when a session ends partway: in a new session at the workspace, "continue" (or the same request again) carries on with `run next`. `run start` carries on only with an unfinished run of the same workflow and brands, started the same way (a scheduled task never takes over a conversation's run, or the other way round). **Brands a run was finished without stay to do**: `run finish --partial`, and a run closed when a new day's or week's run starts, leave them as Caiman's own unfinished work (`still_to_do`), never as something for the member to decide. The next `run start` of the same workflow puts them first, and `run next` (with no unfinished run, or naming the finished run) and `plan` carry them on first in a new run of that workflow, without asking; each picked-up brand is marked in the finished run (`picked_up_in`), and one a later run of the workflow has isn't carried again. The finished run's note and answer then say where it was picked up ("Picked up in the run ..."), finishing that run again never puts it back to do, and `run next` naming that run carries on in the run that picked it up while it's open. A daily workflow's brands from an earlier day go first in its next run, and start fresh there (that day's work is over: no "carry on from there", and no claim of that day's session), but aren't offered on their own; another workflow's are offered for six days.

**A brand in progress stays with the session that has it.** Each brand is handed to one session (a conversation, or one scheduled run) until it's recorded, and that session gets it back first; two sessions never do one brand at once. When another conversation comes to a brand another session was handed less than 30 minutes ago, it leaves it to that session and goes on with the next brand, saying so (`held.left`). A brand another session has had for 30 minutes or more without recording it (most often a chat that stopped) it carries on without asking, as Caiman's own unfinished work: the answer says so (`held.taken_over`: which session, since when, with the usual reminder to check its folder for what was already done) and offers one choice, `leave-it` (`run next --leave <brand>`), for when the member says that session is still working on it: the brand goes back to that session and this one gets the next brand. When only brands another session has are left, `run next` says so (`brands-in-progress-elsewhere`) and asks the one real question, whether that session stopped: if it did, take it over (`--take-over <brand>`); if not, finish when that session has recorded it, or `run finish --partial` for the note now (the brand stays to do). A scheduled run never asks: it leaves a brand another session has and moves on, saying so, and when only such brands are left it stops without finishing (that session finishes the run); a brand another session has had for three hours or more without recording it is taken over (that session most likely stopped), and the answer says so. A brand another session had when its run was finished keeps that claim, for up to three hours, in the run that picks it up (the same rules apply there), and that session's `run done` (or `run reports`) on the finished run is recorded in that run. `run done` warns when a session records a brand another session has. Runs of the daily workflows (the Advertising Daily Check and the VIP Machine's daily brief and health check) start fresh each day, and the others after six days; an unfinished run from earlier is closed, its remaining brands still to do. `run start ... --new` starts a fresh run on purpose.

**Keep the conversation small.** Finish a brand and save its summary before starting the next. Don't carry one brand's reports or tables into the next brand's work: its summary file is what carries over. In a long run, it's fine to carry on in a new chat: "continue" picks up at the next brand.

## Hard rules: never mix brands

- **Each brand's work happens in its own business folder with its own account.** Use the brand's own connector brand slug for every connector call, and its own Ads profile and seller account. Never pass one brand's slug, profile or seller ID while working on another, never save one brand's reports or files in another brand's folder, and never use one brand's numbers in another brand's proposals or summary.
- **One brand failing or needing an answer doesn't stop the others.** Record it (failed or needs-answer, with what is needed), go on with the next brand, and list it at the end.
- **Each brand's normal approvals still apply** (the caiman skill, section 5). Every change is shown with its brand named ("Acme Outdoors: these four bid changes..."; the combined handoff numbers them across the brands, the brand on each line), and a go covers exactly the lines it names ("go": every line shown), never a change that isn't listed or another brand's change. Scheduled runs never change an account.
- **Brands sharing an account** use only their own products from that account's reports (above). **Two folders for one brand** are left out of runs until the member says which is current.

## Scheduled tasks: one per routine, for every brand

One scheduled task per routine covers all the brands: for example the daily ads check, the Weekly Growth Review, and on VIP each of the VIP Machine's routines, run brand by brand. Each uses the run flow with `--scheduled`, and reuses each brand's own workflow or routine prompt.

- `routine list` shows the all-brands routines with suggested timing and which brands each would cover, and on VIP which of each brand's own VIP Machine routines are on.
- `routine prompt <workflow>` prints the prompt for one (`advertising-daily-check`, `weekly-growth-review`, `advertising-weekly-review`, `vip-daily-brief`, `vip-health-check`, `vip-weekly-loop`, `vip-opportunity-review`).
- Create a task only after the member approves its timing and time zone, the workspace folder it runs in, and its notifications. Create it with the prompt as printed: it finds `workspace.py` in the caiman skill when it runs, so a plugin update doesn't break it, and in the Claude app's Linux workspace (where connected folders are under `/sessions/<session>/mnt/`, a folder that changes every session) it names the workspace as `$HOME/mnt/<folder>`, where every session finds it. Read the task back to check it was saved as agreed.
- **VIP Machine routines** still need each brand's own approval record: save it in that brand's `SCHEDULE_PLAN.json` as its `SCHEDULED OPERATIONS.md` says, with that brand's business folder, and set the routine's `enabled` in that brand's VIP Machine settings (its `schedules/README.md`, step 5). Kit updates keep a routine on only when that plan shows it.
- If a brand already has its own scheduled task for the same routine, the all-brands task replaces it: with the member's OK, remove the brand's own task so the routine doesn't run twice.

## The files

In the workspace folder: `CAIMAN WORKSPACE.json`, the workspace section of `CLAUDE.md`, `START HERE - all brands.md`, `CAIMAN STATUS.md` (the setup check for all brands), `WORKSPACE PLAN.md` and `.json`, `WORKSPACE SUMMARY.html` and `.md`, and `workspace-runs/` (each run's record, its combined note, and a folder with each brand's summary and handoff). Nothing in a brand's business folder changes except what that brand's own workflow writes there, as usual.

If the brand folders are on the member's computer, run `workspace.py` there, as kit-sync's guide says for `kit_sync.py`: copy it across (with `kit_sync.py` for `update` and `update-plan`, named with `--kit-sync`; a path relative to the folder you run it from works, as does one for `--zip`) and add `--plugin-version <this plugin's version>`, which a copy can't read for itself.
