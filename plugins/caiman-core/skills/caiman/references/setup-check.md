# Setup check

## Every session: the setup check

Every session starts with this check (the caiman skill, section 1). It says "everything's working" or exactly what isn't, and saves that for the member in `CAIMAN STATUS.md` in the business folder.

1. Call the Caiman connector's `list_brands`, and save its whole answer to a temporary file exactly as it came back: outside the business folder when you can, and never in its `.caiman` or `Reports` folders. This check and the trial week check (the caiman skill, section 1) both read that file.

   Then, when the folder has a kit, call `get_kit_download` for its membership (`plan_tier` in the folder's `ENTITLEMENTS.json`: `vip`, or `gls-plus` for GLS+). Its first line names the kit members get now, for example `release 2026-10-14-vip-v56`. Pass that release with `--live-kit`, so the check compares the folder's kit with it and not only with this plugin. At a workspace, call it once for each membership its brands have and pass `--live-kit` once for each. Don't save that result in the business folder: its link is a short-lived credential. When the tool isn't listed or fails, run the check without `--live-kit` and carry on. Then test Caiman's download site where the kit's scripts run, every session (kit updates and the VIP Machine's weekly refresh download from it): `curl -sS -o /dev/null -w "%{http_code}\n" https://tools.caimandata.ai`. Any answer from the server, even 404, is `--download-site ok`. A refusal ("CONNECT tunnel failed, response 403", or the network refused the connection) is `--download-site blocked --download-error "<the refusal>"`: the check then names Claude's network setting with the member's click, and the Kit and VIP Machine lines say what waits for it (section 3). With no command tool to test with, leave both out.
2. Run the check where the business folder is, with what `list_brands` gave: `ok` with every brand slug it returned (`""` when it returned none) and its brands as JSON, `failed` and the error text, or `not-connected` when no Caiman connector tools are listed.

   ```
   python3 "<caiman skill folder>/scripts/setup_check.py" --project-root "<business folder>" \
     --connector ok|failed|not-connected --connector-brands "<slug,slug,...>" \
     --connector-brands-json @<list_brands answer file> \
     [--live-kit <release from get_kit_download>] [--connector-error "<text>"] [--download-site ok|blocked] [--download-error "<text>"]
   ```

   At a workspace (the folder holds several brands' business folders; the caiman skill's workspace guide), pass the workspace folder as `--project-root`: each brand is checked in its own folder, and the answer has one headline for all of them. When the folder has no kit and its business folders are more than three levels down, the business folder check says where they are: work from that folder instead (never install a kit in this one).

   Pass `--connector-brands-json` that file, unchanged: the check reads each brand's `slug`, `display_name`, `marketplace_id`, `sp_api_authorized` and `ads_authorized` from it. With the names, the check can tell a folder an older kit saved under an earlier account name from another brand's, and with the last two it can tell a connection that's off; `--connector-brands` alone still works without them. On Windows, use `py -3` (the caiman skill's "Which Python command"). It usually takes seconds; allow it up to three minutes. `--no-write` leaves `CAIMAN STATUS.md` alone.
3. Open your first reply with its `headline` ("Setup check: everything's working." or "Setup check: 2 things need attention: ...") and, for each item, what you're doing about it. A `problem` blocks the work that needs it: deal with it first, or ask for the click only the member can make. An `attention` item doesn't block: say it, and take care of it when the work reaches it. **A kit update comes first, every time:** when the Kit line says the kit needs an update (older than this plugin, or older than the kit members get now), do it straight away with kit-sync, before Deep Seed or anything the member asked for, without asking first (say in one sentence that you're updating it; it keeps their files). Then run the check again. At a workspace, "Update all my brands" (kit-sync's guide) does every brand that needs it. In a scheduled or routine run, don't update: say in the run's summary that a kit update is due, and the next session with the member does it.
4. **Report the versions.** The answer's `kit_report` is a call for the Caiman connector's `record_kit_state` tool: the plugin's version and each folder's kit version and status, nothing about the business. When the connector lists that tool, call it once with exactly those arguments after each check; otherwise skip it. Don't retry it. If the member asks, say that Caiman's setup check tells Caiman which plugin and kit versions the folder has, so members can be kept up to date.

It prints JSON: `status` (`ok`, `attention` or `problem`), `headline`, `status_file` and `checks`, each with a `member_line` in plain words, a `next_step` for you and `details` (for example which reports are due). It changes nothing but `CAIMAN STATUS.md` and, when the folder has a `.caiman` folder, `.caiman/setup-check.json` (the same result for the kit's scripts: `NEXT_STEP.py` reads the business's Amazon connections from it), and never uses the network. `CAIMAN STATUS.md` says when it checked in the computer's local time; when the computer's clock is set to UTC (the Claude app's Linux workspace, a cloud task), it uses the member's time zone when the folder records one (a `Time zone` line in `CLIENT_RULES.md`, or the routines' zone the member approved in `SCHEDULE_PLAN.json`), else the Amazon account's (the saved Ads profile read, or the marketplace's), and otherwise says UTC. The checks:

- **Commands and Python.** Below Python 3.8 is a problem: install a newer one (the caiman skill, "Which Python command").
- **Business folder.** Saving `CAIMAN STATUS.md` is the test that Claude can write there. A folder that's missing, or that Claude can't save in, is a problem: section 1.
- **Kit.** From kit-sync `status` (without kit-sync, `core_version` against this plugin's version), then against the kit members get now (`--live-kit`): a newer release there is a kit update due now (`details.kit_status: update_due`), even when the folder's kit matches this plugin. No kit is a problem: install it with kit-sync. Anything kit-sync would act on is attention (older, skills missing or not the kit's version, VIP Machine or CLAUDE.md older, `CLIENT_RULES.md` without the kit's block of Caiman's rules, files from earlier kits): update with kit-sync. A kit newer than the plugin is attention too (the member updates the plugin), and so are skills that can't be checked or are locked (section 4; kit-sync's guide).
- **Caiman connector.** From `list_brands` and this business's saved account (VIP: `brand.slug` in `VIP Machine/config/brand.json`; both memberships: the account saved with the source list). Not connected, failed, no account, or not this business's account is a problem: section 5. When `list_brands` shows the business's store with a connection its membership needs switched off (`sp_api_authorized` or `ads_authorized` false; VIP needs both, GLS+ needs Amazon Ads), the check names it and the click only the member can make: connect it in their Caiman account, which Amazon takes about a day to switch on (connect today, live tomorrow), so ask for it in your first reply. It is a problem when it blocks what the membership reads (Seller Central on VIP, Amazon Ads on GLS+) or a set-up VIP Machine's weekly reports; Amazon Ads before the VIP Machine is set up is attention: Deep Seed carries on from Seller Central, and the VIP Machine, its last step, waits for Amazon Ads (its line says so, and so does `NEXT_STEP.py`). No account chosen yet is fine, and so is a files-only view (`local-…`). A source list an older kit saved under another kind of account ID (an Ads profile ID or seller ID, not shaped like a `list_brands` slug) is attention, not a problem: keep using it for that folder's files and confirm which brand the folder is before pulling data; reconnecting the store won't change it. A slug that isn't listed is another brand's, or an old slug: that stays a problem (section 5), unless the folder's saved brand name matches exactly one listed brand's `display_name` (ignoring case, spaces and punctuation) and its marketplace matches that brand's. Then it's attention: the folder is saved under an older account name, and `details.looks_like` names the brand it looks like. Confirm with the member that the folder is that brand before pulling data; then read the connector with the listed slug and keep registering the folder's reports under the saved account name. A VIP Machine's `brand.slug` that isn't listed is a problem, unless the machine is linked to a slug that is listed: then it's ok ("shows this business's Amazon account (Brand), connected as <slug>"), and `details.connector_slug` names the slug to use for connector calls. A link to a slug that's no longer listed (the store was connected again), or a link that doesn't check out, stays a problem: section 5.
- **Deep Seed.** No business view (`operating-view.json` under `Reviews/`) is attention: offer to finish Deep Seed. On VIP outside US dollars, a saved read-only review with sales by product (the kit's `READ ONLY REVIEW.md`) counts as Deep Seed done, as it does for `NEXT_STEP.py`.
- **VIP Machine** (VIP). Not set up, setup not finished, or reports due for a refresh is attention. Reports due never stop the work: the weekly review, a scheduled one too, refreshes them first with the kit's `WEEKLY_REFRESH.py` (`plan`, the connector reads it lists, then `finish` until it answers ready). Blocked, or a check that can't run, is a problem. Its `next_step` names the guide to follow. A VIP Machine set up but with no scorecard yet says so, with the day its setup finished: it tracks no proposals or changes until the weekly review builds the scorecard, so say that plainly and make that weekly review the next step.
- **Caiman's download site** (only with `--download-site blocked`). A problem: kit updates and the VIP Machine's weekly refresh can't download. Ask for the member's click in your first reply (section 3), and say that the kit update and the weekly refresh wait for it; meanwhile a kit update installs from the kit zip in their Caiman account. Never call it the member's own network unless the download ran directly on their computer (Claude Code).
- **Star ratings** (VIP, when the VIP Machine records them). No reading from the last 30 days is attention: no connector tool returns ratings, so read each product's star rating and rating count from its Amazon page with a browser tool if you have one, or ask the member for the two numbers under the product title, and save them with the VIP Machine's `record-ratings`.
- **Old skill copies.** Each skill named like one of the kit's (or the plugin's) that loads from outside the business folder, as far as this computer shows: the account's skills (synced into a cloud session, or the account folders it mounts) and Claude Code's personal skills folder, with the date the account's list shows for each. The plugin's own folders aren't looked in, and a copy marked with this plugin's Caiman version (or a later one) isn't old. It is attention, never a problem, and there's no line when it finds none or can't see those places. Use the business folder's `.claude/skills/<name>/SKILL.md` for each (for caiman and kit-sync, the plugin's own skill), even though a same-named skill is listed, and tell the member once how to remove them (section 7).

**When the check can't run.** If commands can't run at all, that is the setup check's result ("Setup check: Claude can't run commands on your computer yet, so Caiman's tools can't run."). Get them running (section 2), and meanwhile check by hand with your file tools and write `CAIMAN STATUS.md` yourself in the same shape: the headline, when you checked, one line per check with ✅, ⚠️ or ❌, and what happens next, in plain words, with no account IDs, links or error codes. From the files: no `RELEASE_MANIFEST.json`: the kit isn't installed; its `core_version` older than this plugin's `version` (in `.claude-plugin/plugin.json`): the kit needs an update. The connector: from `list_brands`, as above. No `operating-view.json` under `Reviews/`: Deep Seed hasn't finished. On VIP, no `VIP Machine` folder: the VIP Machine isn't set up; `bootstrap: true` in its `state/workspace.json`: its setup isn't finished; otherwise its data couldn't be checked. Say which lines you checked by hand. If commands run on the member's computer but can't reach this skill's `scripts` folder (a task in the cloud), copy `setup_check.py` to that computer as kit-sync's guide says for `kit_sync.py` (it needs no other file) and add `--plugin-version <this plugin's version>`, which a copy can't read for itself; or check by hand as above.

## When setup is new or stuck

Use this when a member sets up Caiman for the first time, when they come back to a setup that isn't finished, whenever setup stalls (a step keeps asking for approval, the folder looks empty, a download or a copy fails, or the member says they've been at it for a while), and when they ask you to check their Caiman setup. Setup usually stalls on Claude's settings or the member's computer rather than on Caiman, most often on these two: network access for code that doesn't allow Caiman's download site (section 3), and Claude's workspace not running on the member's computer (section 2). Check both early, so the member makes those changes together with the other clicks instead of halfway through an install (section 3 says how to check the network).

Offer to do the setup yourself, then do it, for example: "I can set this up for you. You'll see a few approval prompts; approve them and I'll do the rest." Do every step you have a tool for. Ask the member only for what needs their own click, one step at a time, and say where to click. Menus differ between app versions and plans: if the member doesn't see what you describe, ask what they see and go from there. Don't hand them a list of steps you could do yourself.

## 1. The business folder

- Check that you can see it. In Claude Code it's the folder Claude was started in. In the Claude app it's a folder added to the chat or to its project.
- If you can't see it, ask where it is (for example `C:\Users\<name>\Desktop\<Brand>` or `~/Documents/<Brand>`), then ask for access yourself with the app's folder-access tool; the member only approves the prompt. If that tool isn't available, ask them to add the folder to the chat (in the Claude app, usually from the + menu beside the message box).
- In a Claude project, the folder should belong to the project, so every chat in it can reach the files. If each new chat says no folder is connected, ask the member once to add the business folder to the project.
- The business folder holds the kit (`CLAUDE.md` and `CAIMAN_CURRENT.md`; on VIP, also the `VIP Machine` folder once setup has made it), or it's an empty folder chosen for a new business. A folder of reports or notes isn't it; those files can be brought in later.

## 2. Where commands run

- When the folder is on the member's computer, run the kit's scripts on that computer, with the app's command tool for it. That tool runs in Claude's workspace, a small Linux virtual machine the Claude app keeps on the computer, with Python built in. In Claude Code on Windows, commands run on Windows itself; the caiman skill's "Which Python command" says what to run there.
- **If you can reach the computer's files but there's no command tool for it, or it says "Workspace unavailable",** Claude's workspace isn't running on that computer. It's a setting on the computer. Don't tell the member it's their plan or account, or that tasks in the cloud can't run commands: they can, once the workspace runs. Don't work around it with screen control (the computer-use tools): no double-clicking scripts or installers in File Explorer or Finder, and no clicking through the computer's settings. Members find their screen being taken over confusing, and the fix below is what lets everything run in the background. Don't ask the member to run Caiman's scripts by hand either: on Windows, the fix file below is the one thing they double-click.
  - **Windows:** if `claude-workspace-fix.txt` is already in the business folder, the member has run the fix. Read it, do what it says that you can, and go to the last step if the workspace is still down. Otherwise copy `windows-workspace-fix.cmd` from this folder into the business folder as `Fix Claude Workspace.cmd`, with your file tools (in a task in the cloud, the tool that saves files to the member's computer). Copy the file itself; don't retype it. If you can't write it there, give it to the member as a file in the chat and ask them to save it in the business folder. Then ask, in one message: "Double-click Fix Claude Workspace in your business folder and click Yes when Windows asks. Do what it says at the end (usually restart your computer), then start a new task here and say: continue." It starts the Claude VM Service, turns on Virtual Machine Platform and turns the Windows hypervisor back on when that's what blocks it, and it tells the member about anything only they can do: virtualization in the BIOS, reinstalling Claude, updating Windows or freeing space. It saves what it found and did in `claude-workspace-fix.txt`.
  - **Mac:** go through these in order, one message each, and don't repeat a step the member says they've done (quitting and reopening is the usual first try; on its own it rarely fixes an Intel Mac).
    1. **Update Claude.** Ask the member to click the Claude menu (top left, beside the Apple menu), choose Check for Updates, install what it offers and relaunch Claude, then start a new task with only the business folder attached (not a whole Dropbox, Documents or Desktop folder). In 2026 a Claude app update kept the workspace from starting on Intel Macs until a later build fixed it, and some Intel Macs got that build only through Check for Updates; quitting, resetting or reinstalling didn't help. A big synced folder attached to the task can also make the workspace take longer to start than the app allows.
    2. **Two screenshots.** If it still won't start, ask for a screenshot of About This Mac (Apple menu, About This Mac: it shows the chip, Intel or Apple, the year and the macOS version) and of Anthropic's readiness check (https://claude.ai/api/desktop/darwin/universal/cowork-readiness-check/latest/redirect), which names what's missing. Read both, and check that the Mac has about 20 GB free (Apple menu, System Settings, General, Storage). Do what the check names that the member can do, then ask them to start a new task again.
    3. **Claude Code on the Mac.** If the workspace still won't start, or the check says this Mac can't run it, Caiman runs in Claude Code on that Mac instead: commands run on macOS itself, so the workspace isn't needed. It's the same Claude account, so the Caiman plugin and the connection come with it, and the business folder and kit stay as they are. Give the member the steps below one at a time and wait for each; you can't do them from this task (and never through screen control). If they'd rather not use Terminal, offer Caiman support to walk them through it.
       1. It needs macOS 13 or newer (About This Mac shows the version) and the paid Claude plan the app's tasks already use. On an older macOS, the member updates macOS first if the Mac can, or asks Caiman support.
       2. Open Terminal (press Cmd+Space, type Terminal, press Return).
       3. Paste `curl -fsSL https://claude.ai/install.sh | bash` and press Return. It shows nothing while it downloads; wait for it to finish, then quit Terminal and open it again.
       4. Type `cd` and a space, drag the business folder from Finder into the Terminal window, and press Return.
       5. Type `claude` and press Return (if Terminal says the command isn't found, type `~/.local/bin/claude`). Sign in with the same Claude account as the app when the browser opens.
       6. The Caiman plugin comes from the account and syncs when Claude Code starts. If Claude Code says "Plugins changed. Run /reload-plugins to activate.", type `/reload-plugins`. If Caiman still isn't there, type `/login`, sign in again, type `/exit` and start `claude` again in the folder.
       7. Type `/mcp`. If the Caiman connector (`caiman-amazon`) says it needs signing in, pick it and sign in with the Caiman account in the browser. A Caiman connector added in Claude's settings on the web shows there too, already connected.
       8. The first time Caiman's tools run, the Mac may ask to install the "command line developer tools": click Install (a few minutes, once), then tell Claude to continue.
       9. Then say "Check my Caiman setup". The setup check and kit-sync run there as in the app (the caiman skill's "Which Python command").
  - If it still won't run on Windows either, tell the member plainly what the fix file said, and that installing or updating the kit, Deep Seed and the VIP Machine wait until it does. Don't run them in this session's own workspace and copy the results across: an install there can't see the member's files, so a copy back could overwrite them without saving the old versions. Don't run them through screen control either. If the workspace can't run on that computer at all (for example, virtualization is locked by whoever manages it), say so and offer the ways forward: Claude Code on that computer, where commands run on the computer itself (the caiman skill's "Which Python command"; on a Mac, the steps above), or Caiman support.
- **If you have no tools for the member's computer at all,** this task isn't connected to it. Ask the member to open the Claude desktop app on the computer that has the business folder, signed in, and to continue the task from there.

## 3. The kit download

kit-sync gets the kit through the Caiman connector's `get_kit_download`. To check early, run `curl -sS -o /dev/null -w "%{http_code}\n" https://tools.caimandata.ai` where the download will run: any answer from the server, even 404, means it can be reached; "CONNECT tunnel failed, response 403" means Claude's network setting blocks it (item 1 below). If a network refuses the Caiman download server, kit-sync says so (for example "Tunnel connection failed: 403") and names the host it tried, normally `tools.caimandata.ai`. That's a network setting, not Caiman. Give the member the two ways, in this order:

1. If the download ran in Claude's workspace (a task in the cloud, or the workspace the Claude app runs on the member's computer), Claude's network setting for code blocks it. The member allows that host in Claude's Settings, under Capabilities: under Code execution and file creation, turn on Allow network egress, and if there's a domain list, choose All domains or add the host. On a Team or Enterprise plan an owner changes it in Organization settings, under Capabilities; if the member doesn't see the setting, that may be why. With it allowed, kit-sync can download later updates itself. Then try again, and if it's still refused, in a new task. Only when the download ran directly on the member's computer (Claude Code) does their own network or proxy block the site, and whoever manages that network can allow it.
2. Or the member downloads the kit zip from their Caiman account (the membership download) and saves it, without unzipping, in the business folder. Install from that zip. On a Mac, Safari may unzip downloads by itself (Safari Settings, General, "Open safe files after downloading"); if the member ends up with a folder instead of a zip, ask them to turn that off and download again, or to use another browser.

Don't try to reach the server another way, and don't install the kit file by file through the connector.

## 4. The skills folder

The kit's skills go in `.claude/skills/` inside the business folder. Some apps don't let Claude's tools into `.claude`. kit-sync then installs or updates everything else and names the skills it couldn't install (`skills_blocked`). When its `why` is `locked`, the app isn't the cause: another program has a skill folder open, or its permissions keep kit-sync out, so the member closes that program or fixes the permissions and kit-sync runs again (kit-sync's guide, "If a skill folder is locked"). Otherwise:

- Say plainly that only the skills are left, and that this is the one step the member does by hand.
- For this session, use the skills from the kit zip. They're the same files.
- Walk the member through the copy, one step at a time:
  1. Extract the kit zip in Downloads, not in the business folder (download it again from their Caiman account if needed). **Windows:** right-click the zip and choose Extract All. **Mac:** double-click the zip; Safari may already have unzipped it into a folder, which works too.
  2. Open the extracted `Caiman VIP - Guided Kit` folder (`Caiman GLS Plus - Guided Kit` on GLS+; on Windows it's inside a folder named after the zip). It holds a `.claude` folder with a `skills` folder inside. **Mac:** press Cmd+Shift+. (period) to show folders whose names start with a dot. **Windows:** File Explorer normally shows them.
  3. Open the business folder. If it has no `.claude` folder, copy the kit's whole `.claude` folder into it. If it has `.claude` but no `skills` inside, copy the kit's `skills` folder into the business folder's `.claude`.
  4. If the business folder already has `.claude/skills`, first rename that `skills` folder to `skills-old` (add today's date if that name is taken), then copy the kit's `skills` folder into the business folder's `.claude`. Renaming keeps everything that was there, and nothing gets replaced. If the member had made skills of their own in it, they move those folders from `skills-old` back into the new `skills` folder.
  5. If the computer asks whether to replace anything, choose Stop (or Skip) and tell Claude; never choose Replace.
  6. Delete the extracted folder from Downloads, so there isn't a second copy of the kit.
- Then ask the member to start a new chat in the project, so the skills load, and run kit-sync `status`. `current` means the copy worked. `skills-older` or `skills-missing` names skills that still aren't the kit's version. `skills-blocked` means kit-sync can't look inside `.claude` to check; then check that Claude lists the Caiman skills (for example `vip-machine` on VIP).

## 5. The Caiman connector

- `list_brands` should show the member's brand with `sp_api_authorized` and `ads_authorized` true (VIP needs both; GLS+ needs Ads). Use the slug it shows now, and `diagnose_brand` to see whether each connection works.
- If the brand is missing or a connection is off, the member connects it again in their Caiman account; then call `list_brands` again. On VIP, check first whether the business folder has a `VIP Machine`: disconnecting and reconnecting a store gives the brand a new slug, and the VIP Machine knows only its own slug and the one linked to it. Never reconnect a store just to change its slug: it gives yet another slug, never the old one.
- On VIP, when the store is listed under another slug than the VIP Machine's (a machine set up under the business's own name, or a store connected again), link that slug to the machine with the member's go: read `list_ads_profiles` for it, and if its Ads profile, seller and marketplace IDs are the VIP Machine's settings, run `vip_machine.py link-connector-slug`, which checks them first, then give the business view the same link with `PREPARE_OPERATING_INPUTS.py rebind` (the kit's `TROUBLESHOOTING.md`, "The brand's slug changed"). Only when the IDs don't match is it a case for Caiman support. Never change the VIP Machine's settings yourself.
- If no Caiman connector tools are available at all, ask the member to turn on the Caiman connector in the app's connector settings, then continue.

## 6. Approvals and the model

- In Manual approval mode, the app asks before every connector call, and setup makes many read-only calls. If prompts keep coming, or "Always allow" doesn't stop them, suggest switching the approval mode from Manual to Auto for setup (in the Claude app it's usually below the message box). Say plainly what that means: in Auto, the app no longer asks before any call, including ones that change the Amazon account. Claude still waits for the member's go before an account change (the caiman skill, section 5), but the app doesn't enforce that. So suggest switching back to Manual once setup and Deep Seed are done, before ads or listing work.
- Deep Seed is long. If the chat keeps stalling, repeating steps or losing track, suggest picking the most capable model in the model menu.

## 7. Old skill copies and old instructions

Caiman's skills reach a member only two ways, and both are replaced with every release: the business folder's `.claude/skills/` (kit-sync, which the setup check runs) and the Caiman plugin (Customize > Plugins > Update). Nothing goes on the account's Skills page. Copies added there by hand (the July to September 2026 kits had members do it) never update, and some apps list only those.

- **Old skill copies.** When the setup check's Old skill copies line names some, use the business folder's `.claude/skills/<name>/SKILL.md` for each of those skills (for caiman and kit-sync, the plugin's own skill), even though a skill with the same name is listed. Tell the member once, with the steps: in Claude, Customize > Skills > the skill > Delete, once for each; for a copy in Claude Code's own skills folder on their computer, delete or move that folder. Don't stop the work for it.
- **Old instructions.** If the member's Claude preferences, project instructions or saved memory still hold setup steps from those kits (adding Caiman's skills to the account one by one, or presenting voltage-setup first), say they're from an earlier kit and now get in the way, and offer the exact lines to remove. The `voltage-setup` skill itself (VIP) is current; only those old steps around it are out of date. Follow the kit's `CLAUDE.md` and this plugin instead.

## 8. Say where things stand

Run the setup check again (the top of this guide), then say in a few lines: the business folder, the plugin and kit versions and whether both are current (the setup check's Kit line, which compares the kit with this plugin and with the kit members get now), the connector, and anything the member still has to do. Then run the guide folder's `NEXT_STEP.py --project-root "<business folder>"` and offer its next step, as the caiman skill says: Deep Seed for a new business, and otherwise whatever the plan has next.
